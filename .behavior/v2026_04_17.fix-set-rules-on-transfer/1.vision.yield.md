# vision: declarative cloudflare domain redirect rules

## the outcome world

### before
- transfer a domain to Cloudflare, then manually log into dashboard to set up redirect rules
- forget to add "redirect http to https" on new domains - users hit insecure warn
- forget to add "redirect root to www" - SEO splits between apex and www
- each domain requires manual clicks through Cloudflare UI
- no audit trail of what rules exist where

### after
- declare redirect rules alongside domain registration in code
- `declastruct apply` ensures all domains have consistent redirect policies
- new domains automatically get redirect rules applied
- git history shows when rules were added/changed
- drift detection alerts if someone manually changes rules

### aha moment
"I just transferred 12 domains and they all have consistent redirect rules without a single touch of the Cloudflare dashboard."

## user experience

### usecase: consistent redirect policy across domains

**goal**: ensure all domains redirect http->https and root->www

**contract input** (resources file):
```typescript
import { refByUnique } from 'domain-objects';
import {
  DeclaredCloudflareDomainZone,
  DeclaredCloudflareDomainRuleRedirect,
  RULE_REDIRECT_SPEC_HTTP_TO_HTTPS,
  RULE_REDIRECT_SPEC_ROOT_TO_WWW,
} from 'declastruct-cloudflare';

export const getResources = async () => {
  const domains = ['example.com', 'example.org', 'example.net'];

  return domains.flatMap((domainName) => {
    const zone = new DeclaredCloudflareDomainZone({
      name: domainName,
      type: 'full',
    });

    return [
      zone,
      new DeclaredCloudflareDomainRuleRedirect({
        zone: refByUnique(zone),
        slug: 'force-https',
        spec: RULE_REDIRECT_SPEC_HTTP_TO_HTTPS,
      }),
      new DeclaredCloudflareDomainRuleRedirect({
        zone: refByUnique(zone),
        slug: 'apex-to-www',
        spec: RULE_REDIRECT_SPEC_ROOT_TO_WWW,
      }),
    ];
  });
};
```

### usecase: custom redirect rule

**goal**: redirect old domain to new domain

```typescript
new DeclaredCloudflareDomainRuleRedirect({
  zone: refByUnique(zone),
  slug: 'legacy-domain-redirect',
  spec: new DeclaredCloudflareDomainRuleRedirectSpec({
    expression: '(http.host eq "old.example.com")',
    parameters: {
      fromValue: {
        targetUrl: { expression: 'concat("https://new.example.com", http.request.uri.path)' },
        queryString: 'preserve',
        statusCode: 301,
      },
    },
  }),
})
```

## domain objects

### DeclaredCloudflareDomainRuleRedirectSpec (DomainLiteral)

```typescript
/**
 * .what = spec for a cloudflare redirect rule
 * .why = typed config for redirect rules
 *
 * .note
 *   - camelCase internally, DAO transforms to cloudflare's snake_case
 *   - DomainLiteral = no identity, just typed value
 *   - parameters.fromValue = inline redirect target
 *   - parameters.fromList = bulk redirect list lookup (future)
 */
export interface DeclaredCloudflareDomainRuleRedirectSpec {
  expression: string;
  parameters: PickOne<{
    fromValue: {
      targetUrl: { value: string } | { expression: string };
      queryString?: 'preserve' | 'ignore';
      statusCode?: 301 | 302 | 303 | 307 | 308;
    };
    fromList: {
      name: string;
      key: { expression: string };
    };
  }>;
  enabled?: boolean;
}

export class DeclaredCloudflareDomainRuleRedirectSpec
  extends DomainLiteral<DeclaredCloudflareDomainRuleRedirectSpec>
  implements DeclaredCloudflareDomainRuleRedirectSpec {}
```

### DeclaredCloudflareDomainRuleRedirect (DomainEntity)

```typescript
/**
 * .what = a cloudflare redirect rule within a zone's ruleset
 * .why = enables declarative redirect rule management
 *
 * .identity
 *   - @primary = [id] — assigned by cloudflare on creation
 *   - @unique = [zone, name] — composite unique within zone
 *
 * .note
 *   - rules live in the `http_request_dynamic_redirect` phase ruleset
 *   - `name` maps to cloudflare's `description` field
 *   - zone is a Ref, enables declaration before zone exists
 */
export interface DeclaredCloudflareDomainRuleRedirect {
  // identity
  id?: string;  // @metadata — assigned by cloudflare
  zone: RefByUnique<typeof DeclaredCloudflareDomainZone>;  // @unique
  slug: string;  // @unique — our identifier, maps to cloudflare's `description`

  // rule config
  spec: DeclaredCloudflareDomainRuleRedirectSpec;

  // metadata
  createdOn?: string;  // @readonly
  modifiedOn?: string;  // @readonly
}

export class DeclaredCloudflareDomainRuleRedirect
  extends DomainEntity<DeclaredCloudflareDomainRuleRedirect>
  implements DeclaredCloudflareDomainRuleRedirect
{
  public static primary = ['id'] as const;
  public static unique = ['zone', 'slug'] as const;
  public static metadata = ['id'] as const;
  public static readonly = ['createdOn', 'modifiedOn'] as const;
  public static nested = { spec: DeclaredCloudflareDomainRuleRedirectSpec };
}
```

### preset specs (v1 scope)

```typescript
// http -> https redirect
export const RULE_REDIRECT_SPEC_HTTP_TO_HTTPS = new DeclaredCloudflareDomainRuleRedirectSpec({
  expression: '(http.request.uri.scheme eq "http")',
  parameters: {
    fromValue: {
      targetUrl: { expression: 'concat("https://", http.host, http.request.uri.path)' },
      queryString: 'preserve',
      statusCode: 301,
    },
  },
});

// root (apex) -> www redirect
export const RULE_REDIRECT_SPEC_ROOT_TO_WWW = new DeclaredCloudflareDomainRuleRedirectSpec({
  expression: '(not starts_with(http.host, "www."))',
  parameters: {
    fromValue: {
      targetUrl: { expression: 'concat("https://www.", http.host, http.request.uri.path)' },
      queryString: 'preserve',
      statusCode: 301,
    },
  },
});
```

## mental model

### how users describe it
"I declare what redirect rules I want on each domain, and declastruct makes it happen."

### analogies
- like DNS records but for HTTP behavior
- same pattern as `DeclaredCloudflareDomainDnsRecord` but for redirects
- preset specs are like MX record templates

### user terms vs our terms
| user says | we say |
|-----------|--------|
| "redirect rule" | `DeclaredCloudflareDomainRuleRedirect` |
| "rule config" | `DeclaredCloudflareDomainRuleRedirectSpec` (DomainLiteral) |
| "rule slug" | `slug` (maps to cloudflare `description`) |
| "http to https" | `RULE_REDIRECT_SPEC_HTTP_TO_HTTPS` preset |
| "root to www" | `RULE_REDIRECT_SPEC_ROOT_TO_WWW` preset |
| "the domain's rules" | zone's `http_request_dynamic_redirect` phase ruleset |

### our terms vs cloudflare terms
| our term (camelCase) | cloudflare term (snake_case) |
|----------------------|------------------------------|
| `slug` | `description` |
| `parameters` | `action_parameters` |
| `parameters.fromValue` | `action_parameters.from_value` |
| `parameters.fromList` | `action_parameters.from_list` |
| `targetUrl` | `target_url` |
| `queryString: 'preserve'` | `preserve_query_string: true` |
| `queryString: 'ignore'` | `preserve_query_string: false` |
| `statusCode` | `status_code` |

DAO transforms between our camelCase and cloudflare's snake_case at the API boundary.

## evaluation

### how well does it solve the goals?
- **goal 1 (http->https redirect)**: fully solved via preset + raw spec access
- **goal 2 (root->www redirect)**: fully solved via preset + raw spec access
- **goal 3 (custom rules)**: fully solved via raw expression/action fields

### pros
- follows extant `DeclaredCloudflareDomainDnsRecord` pattern exactly
- exposes full Cloudflare API power via raw fields
- presets for common cases reduce boilerplate
- `name` as unique key enables stable identity

### cons
- requires Cloudflare expression knowledge for custom rules
- preset expressions may need adjustment for edge cases

### pit of success
- TypeScript types constrain `statusCode` to valid values
- `refByUnique(zone)` ensures zone reference is valid
- presets encode best practices (301, queryString: 'preserve')
- `queryString: 'preserve' | 'ignore'` is more explicit than boolean

## open questions & assumptions

### assumptions
- Cloudflare SDK v5.2.0 supports zone rulesets (confirmed via research)
- API tokens can be scoped to "Zone - Rules - Edit" permission (confirmed via repo docs)
- redirect rules are zone-level, not account-level (confirmed via API structure)
- `slug` → `description` map is stable (Cloudflare doesn't use description as unique key, we enforce uniqueness ourselves)

### questions to validate with wisher
1. [answered] are these two presets (http->https, root->www) sufficient scope for v1?
   - answer: yes - confirmed by wisher
2. [answered] should we support custom redirect rules beyond presets?
   - answer: yes - expose raw spec fields via `DeclaredCloudflareDomainRuleRedirectSpec`, presets are convenience

### validated requirements
- **preserve query string**: presets use `queryString: 'preserve'` - confirmed by wisher
- **301 permanent redirect**: presets use 301 status code (standard for canonical redirects)

### external research (completed)
- [researched] Cloudflare has "Always Use HTTPS" managed feature, but we use custom rules for declarative control
- [researched] rate limits: 1,200 requests per 5 minutes (sufficient for declastruct usage)
- [researched] `zone.name` is NOT valid in expressions - updated ROOT_TO_WWW to use `(not starts_with(http.host, "www."))`

## what is awkward?

### feels off
- Cloudflare expressions are their own DSL - users need docs for custom rules

### fights mental model
- `slug` maps to cloudflare's `description` field - minor mental translation when a user checks the dashboard

### uncomfortable tradeoffs
- raw expression/action fields mean users can create broken rules
- but to hide them would limit power users
- presets + raw access is the right balance
