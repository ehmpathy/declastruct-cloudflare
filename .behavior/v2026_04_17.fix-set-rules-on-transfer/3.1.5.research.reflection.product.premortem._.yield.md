# premortem: declarative cloudflare redirect rules

## premortem: imagine we shipped and it failed

project forward: we shipped this, and it failed badly. why?

### failure scenario 1: ruleset PUT wipes extant rules

**what happened**: user ran `declastruct apply` with one redirect rule. the PUT operation replaced the entire ruleset, wiped out 15 extant rules that were created via dashboard or other tools.

**why it failed**: we documented that PUT replaces entire ruleset but users didn't read docs. they expected "add my rule" not "replace all rules with only my rule".

### failure scenario 2: expression syntax breaks in production

**what happened**: preset `RULE_REDIRECT_SPEC_ROOT_TO_WWW` uses expression that works in test but fails on certain edge cases. users deploy, some requests don't redirect, SEO tanks.

**why it failed**: we tested against limited scenarios. cloudflare expression evaluation has edge cases we didn't anticipate.

### failure scenario 3: API rate limits hit in bulk operations

**what happened**: enterprise user with 200 domains runs `declastruct apply`. hits 1,200 request/5min limit partway through. half domains configured, half not.

**why it failed**: we didn't batch operations or implement backoff. user left with inconsistent state.

---

## what obvious signs did we ignore?

- cloudflare's PUT-replaces-ruleset design is documented but we didn't surface it prominently
- we didn't test presets against all edge cases (query strings with special chars, etc)
- no rate limit protection in declastruct core framework
- no validation mode that checks expressions before apply

---

## what assumptions could turn out wrong?

| assumption | what if wrong? | likelihood |
|------------|----------------|------------|
| users only manage rules via declastruct | wipes dashboard-created rules on first apply | medium |
| preset expressions cover common cases | edge cases cause redirect failures | low |
| cloudflare SDK types match API behavior | type says valid but API rejects | low |
| 1,200 req/5min sufficient for typical use | enterprise users hit limits | low |
| `slug` → `description` map is stable | cloudflare changes behavior | very low |
| `not starts_with(http.host, "www.")` is correct expression | syntax differs in production | low |

---

## what is the nightmare scenario?

**scenario**: production site goes down due to redirect loop

**how it happens**:
1. user adds both HTTP_TO_HTTPS and ROOT_TO_WWW presets
2. expressions interact incorrectly — http://example.com redirects to https://example.com redirects to https://www.example.com redirects back
3. browser shows ERR_TOO_MANY_REDIRECTS
4. production site is unreachable
5. user doesn't know how to fix via API, dashboard shows "managed by API"

**why this is worst case**:
- production outage visible to customers
- user may not know how to recover
- trust in declastruct destroyed
- SEO damage from prolonged outage

## what mitigations to consider?

| risk | mitigation | cost of mitigation |
|------|------------|--------------------|
| PUT wipes extant rules | fetch extant ruleset, merge with declared rules | medium — adds complexity |
| PUT wipes extant rules | warn in docs: "declastruct owns entire ruleset" | low — docs only |
| expression syntax breaks | validate expressions via API before PUT | medium — extra API call |
| expression syntax breaks | comprehensive integration tests with presets | low — test effort |
| redirect loop from presets | test preset combinations explicitly | low — test effort |
| redirect loop from presets | document "apply one preset at a time, verify" | low — docs only |
| rate limits hit | implement backoff in provider | medium — adds complexity |
| rate limits hit | document rate limit in operational guidance | low — docs only |
| dashboard conflict | add `managed_by: declastruct` metadata tag if supported | low |

---

## recommended mitigations for v1

### must-have

1. **integration tests with preset combinations** — verify no redirect loops
2. **documentation: declastruct owns the ruleset** — warn users about PUT behavior
3. **error messages surface cloudflare API errors** — don't swallow validation failures

### should-have

4. **fetch-merge-put pattern** — preserve rules not declared in declastruct
   - fetch extant ruleset
   - filter to rules with `description` prefixed by `declastruct:`
   - merge: declared rules replace prefixed ones, others preserved

### nice-to-have

5. **expression validation** — plan mode validates expression syntax via API
6. **rate limit backoff** — exponential backoff on 429 responses
