# research: claims for declarative cloudflare redirect rules

## summary

this document catalogs facts, assumptions, questions, and opinions relevant to declarative redirect rule management for cloudflare domains.

---

## SEO and redirect behavior

### [FACT] 301 redirects transfer SEO signals [1][2][3]

> "Googlebot follows the redirect, and the indexing pipeline uses the redirect as a signal that the redirect target should be canonical" [1]

> "301 redirects should be used to forward traffic from old HTTP URLs to new HTTPS URLs, which sends a strong ranking signal to Google" [2]

**convergence**: sources [1][2][3][4] all agree that 301 redirects transfer ranking signals to the target URL.

### [FACT] www vs non-www causes duplicate content issues [5][6][7]

> "Search engines like Google treat these as two individual websites. If both versions of your site are live and incorrectly set up, your content could appear on both, causing a problem known as duplicate content" [6]

> "This can result in duplicate content issues, split your SEO ranking power, and confuse users and search engines" [5]

### [FACT] redirects are a strong canonical signal [1][5]

> "Redirects (a strong signal that the target of the redirect should become canonical)" [5]

Google treats permanent redirects as canonical indicators, consolidating ranking signals.

### [SUMP] query string preservation matters for analytics [8][9]

> "Usually, query parameters do not survive the redirect process — anything appended to the end of your redirected URL will be stripped" [8]

> "By default, Rank Math passes all the query strings (including the UTM parameters) to the redirected URL" [9]

**assumption**: users expect query strings (especially UTM parameters) to be preserved for analytics tracking.

### [OPIN] use 302 during testing, 301 for production [10]

> "Use 302 (temporary) during testing rather than 301 (permanent), as 301s cache aggressively and are difficult to clear" [10]

## Cloudflare redirect types

### [FACT] Single Redirects operate at zone level [11][12]

> "Single Redirects allow you to create static or dynamic redirects at the zone level (a single domain or subdomain)" [11]

### [FACT] Bulk Redirects operate at account level [11][12]

> "Bulk Redirects allow you to define a large number of redirects at the account level, which can apply across domains in your account" [11]

### [FACT] Single Redirects execute before Bulk Redirects [11][13]

> "If you configure URL redirects using both Single Redirects and Bulk Redirects, the product executed first will apply if there is a rule match (in this case, Single Redirects)" [11]

### [FACT] Single Redirects support dynamic expressions, Bulk do not [11][14]

> "Bulk Redirects are essentially static and do not support string replacement operations or regular expressions" [14]

> "Dynamic Redirects offers almost the entire suite of Ruleset Engine fields for use in filtering" [14]

## API and expression capabilities

### [FACT] max 64 regexes per rule [14]

> "Each rule supports a maximum of 64 regular expressions (regexes), regardless of your domain's plan" [14]

### [FACT] expression language is boolean-based [15]

> "A rule filter expression must evaluate to a boolean value (either true or false)" [15]

### [KHUE] what is the maximum number of redirect rules per zone? [16]

community discussions mention limits but official docs are unclear on exact per-zone rule counts for Single Redirects.

### [KHUE] does zone.name work in expressions? [14]

the vision uses `(http.host eq zone.name)` but this needs verification — some fields may only be available in certain phases.

## Infrastructure as code benefits

### [OPIN] declarative config prevents manual errors [17][18]

> "Manually managing infrastructure becomes error-prone, inconsistent, and impossible to reproduce when infrastructure grows beyond a few resources" [17]

> "With Terraform, you define your infrastructure in simple, declarative configuration files and can check your configuration files into version control" [17]

### [FACT] terraform supports cloudflare redirect rules [18][19]

> "Cloudflare supports URL redirect rules through Terraform's cloudflare_ruleset resource" [18]

> "Using the ref field helps get stable rule IDs across updates and prevents Terraform from recreating the rule on changes" [19]

### [OPIN] version control enables audit trails [17]

> "check your Terraform configuration files into version control and integrate them into your normal software development workflow" [17]

## Plan limits and quotas

### [FACT] Single and Bulk Redirects available on all plans [11]

> "Single Redirects and Bulk Redirects are available on all Cloudflare plans, with exact quotas and features depending on your plan" [11]

### [FACT] Bulk Redirects supports millions of URLs [12]

> "Bulk Redirects supports several million URL redirects" [12]

### [SUMP] free plan has sufficient redirect capacity for typical use [11]

based on documentation, free plans support redirect rules — exact limits may vary.

---

## Anti-patterns

### [FACT] concurrent ruleset updates cause rate limiting [20]

> "You should avoid concurrent updates to the same ruleset, as there are rate limits in place... update the entire ruleset in a single operation instead" [20]

### [FACT] javascript redirects may fail [1]

> "Google cautions against JavaScript redirects, noting: While Google attempts to render every URL Googlebot crawled, rendering may fail for various reasons" [1]

### [OPIN] hidden rulesets can block API/Terraform [10]

> "Rulesets can create invisible conflicts preventing new rule creation via API/Terraform, though the dashboard works fine" [10]

## convergence signals

### strong agreement (3+ sources):
- 301 redirects transfer SEO signals [1][2][3][4]
- www vs non-www causes duplicate content [5][6][7]
- PUT replaces entire ruleset [20][21][22]

### weak agreement (2 sources):
- Single Redirects for zone-level, Bulk for account-level [11][12]
