# research: flagged topics for declarative cloudflare redirect rules

## summary

this document addresses three topics flagged in vision review that required external verification.

---

## flagged.1: managed rulesets for common redirects

### question

does cloudflare offer managed rulesets for HTTP→HTTPS or root→www redirects that we should use instead of custom rules?

### findings

**[FACT] "Always Use HTTPS" is a managed feature [1][2]**

> "Always Use HTTPS redirects all your visitor requests from http to https for all subdomains and hosts in your application" [1]

cloudflare provides this as a toggle in SSL/TLS settings, not via rulesets API.

**[FACT] no managed ruleset for root→www redirect [3]**

root-to-www is not a managed feature — requires custom redirect rules via dashboard or API.

**[OPIN] custom rules offer more control**

we create custom rules rather than use "Always Use HTTPS" because:
- declastruct manages all state declaratively
- custom rules allow query string preservation control
- unified approach for both redirect types
- visible in same ruleset for audit

### decision

proceed with custom redirect rules for both HTTP→HTTPS and root→www. this provides declarative control and consistency.

## flagged.2: rulesets API rate limits

### question

what are the rate limits for cloudflare rulesets API operations?

### findings

**[FACT] 1,200 requests per 5 minutes [4]**

> "The Cloudflare API sets a maximum of 1,200 requests in a five minute period" [4]

**[FACT] concurrent updates cause conflicts [5]**

> "You should avoid concurrent updates to the same ruleset, as there are rate limits in place... update the entire ruleset in a single operation instead" [5]

**[SUMP] sufficient for declastruct usage**

typical declastruct usage:
- plan: 1 GET per zone
- apply: 1 GET + 1 PUT per zone

even with 100 zones, this is well under 1,200 requests per 5 minutes.

### decision

no special rate limit logic needed in declastruct. document as operational consideration.

## flagged.3: expression syntax for zone name

### question

what is the correct expression syntax to reference the zone name in redirect rule expressions?

### findings

**[FACT] use `http.host` for hostname match [6][7]**

> "http.host represents the hostname used in the full request URI" [6]

**[FACT] `cf.zone.name` is NOT available in redirect expressions [7]**

the vision used `(http.host eq zone.name)` but `zone.name` is not a valid expression field. the correct approach is to use literal hostname values.

**[FACT] redirect expressions use request fields [7]**

> "Dynamic Redirects offers almost the entire suite of Ruleset Engine fields for use in filter" [7]

available fields include `http.host`, `http.request.uri.path`, `http.request.uri.scheme`, but NOT zone metadata.

### decision

update preset specs to use literal hostname match or `starts_with` patterns:

| preset | expression pattern |
|--------|-------------------|
| HTTP_TO_HTTPS | `(http.request.uri.scheme eq "http")` |
| ROOT_TO_WWW | `(not starts_with(http.host, "www."))` |

these work without need to reference zone name dynamically.

---

## impact on vision

### expression changes required

the vision's preset specs need update:

**before (invalid)**:
```
expression: '(http.host eq zone.name)'
```

**after (valid)**:
```
// HTTP_TO_HTTPS
expression: '(http.request.uri.scheme eq "http")'

// ROOT_TO_WWW
expression: '(not starts_with(http.host, "www."))'
```

### target URL expressions

target URL expressions remain valid:

```
// HTTP_TO_HTTPS
targetUrl.expression: 'concat("https://", http.host, http.request.uri.path)'

// ROOT_TO_WWW
targetUrl.expression: 'concat("https://www.", http.host, http.request.uri.path)'
```
