# research: cloudflare rulesets API access for redirect rules

## summary

to control domain redirect rules via cloudflare API, we use the **Rulesets API** with the `http_request_dynamic_redirect` phase at the zone level. the official TypeScript SDK (`cloudflare` npm package) provides typed access.

---

## remote repositories

### cloudflare rulesets API

**what**: REST API for zone-level redirect rules
**interface**: HTTPS REST API + official TypeScript SDK
**authentication**: bearer token via `Authorization: Bearer $CLOUDFLARE_API_TOKEN`

---

## API contract

### endpoints [1][2][3]

| operation | method | endpoint |
|-----------|--------|----------|
| create ruleset | POST | `/zones/{zone_id}/rulesets` |
| get ruleset | GET | `/zones/{zone_id}/rulesets/{ruleset_id}` |
| update ruleset | PUT | `/zones/{zone_id}/rulesets/{ruleset_id}` |
| delete ruleset | DELETE | `/zones/{zone_id}/rulesets/{ruleset_id}` |
| get phase entry | GET | `/zones/{zone_id}/rulesets/phases/{phase_name}/entrypoint` |
| update phase entry | PUT | `/zones/{zone_id}/rulesets/phases/{phase_name}/entrypoint` |

> "You can use the phase entry point endpoint when updating a ruleset, avoiding the need to retrieve the ruleset ID first" [3]

### request body structure [1][4]

```json
{
  "name": "Redirect rules ruleset",
  "kind": "zone",
  "phase": "http_request_dynamic_redirect",
  "rules": [
    {
      "ref": "unique_rule_identifier",
      "expression": "(http.host eq \"example.com\")",
      "description": "rule_description",
      "action": "redirect",
      "action_parameters": {
        "from_value": {
          "target_url": {
            "expression": "concat(\"https://www.example.com\", http.request.uri.path)"
          },
          "status_code": 301,
          "preserve_query_string": true
        }
      }
    }
  ]
}
```

### action_parameters structure [1][5]

**dynamic URL (expression-based)**:
```json
"action_parameters": {
  "from_value": {
    "target_url": { "expression": "concat(\"https://\", http.host, http.request.uri.path)" },
    "status_code": 301,
    "preserve_query_string": true
  }
}
```

**static URL (value-based)**:
```json
"action_parameters": {
  "from_value": {
    "target_url": { "value": "https://example.com/contact-us/" },
    "status_code": 308
  }
}
```

### status codes [5][6]

| code | meaning | use case |
|------|---------|----------|
| 301 | permanent redirect | canonical URLs, http→https |
| 302 | temporary redirect | A/B tests, maintenance |
| 307 | temporary, preserves method | API redirects |
| 308 | permanent, preserves method | API redirects |

## SDK access [7][8][9]

### package

```bash
npm install cloudflare
```

### usage

```typescript
import Cloudflare from 'cloudflare';

const client = new Cloudflare({ apiToken: process.env.CLOUDFLARE_API_TOKEN });

// create ruleset
await client.rulesets.create({
  zone_id: 'zone_id_here',
  name: 'Redirect rules',
  kind: 'zone',
  phase: 'http_request_dynamic_redirect',
  rules: [...]
});

// get ruleset
await client.rulesets.get('ruleset_id', { zone_id: 'zone_id' });

// update ruleset
await client.rulesets.update('ruleset_id', { zone_id: 'zone_id', rules: [...] });
```

> "You must provide either account_id or zone_id... You cannot provide both" [8]

## API token permissions [10][11][12]

### required permission

**Zone > Dynamic URL Redirects > Edit** (also called "Single Redirect > Edit")

> "Your token must have Zone | Dynamic Redirect | Edit permission" [13]

### permission hierarchy

| scope | permission | grants |
|-------|------------|--------|
| zone | Dynamic URL Redirects Read | view redirect rules |
| zone | Dynamic URL Redirects Write | create/update/delete redirect rules |

> "Ruleset permissions are at Account Level only and not at Zone Level" [11] — but redirect-specific permissions at zone level do extant.

## best practices

### idempotent updates [14][15]

> "The request replaces the entire ruleset with a new version, so you must include the ID of all the rules you wish to keep. If you omit an extant rule from the rules array, it will not appear in the new version" [14]

**recommendation**: always fetch current ruleset, merge changes, PUT entire ruleset

### avoid concurrent updates [14]

> "You should avoid concurrent updates to the same ruleset, as there are rate limits in place... update the entire ruleset in a single operation instead" [14]

### use ref field for stability [4][16]

> "Use the ref field to maintain stable rule IDs during Terraform updates, preventing unnecessary rule recreation" [16]

**implication**: we can use `description` to look up rules by our slug, but `ref` provides stable identity

### test with 302 before 301 [13]

> "Use 302 (temporary) during testing rather than 301 (permanent), as 301s cache aggressively and are difficult to clear" [13]

## expression syntax [17][18][19]

### common patterns

| pattern | expression |
|---------|------------|
| match host | `(http.host eq "example.com")` |
| match www | `(starts_with(http.host, "www."))` |
| match http | `(http.request.uri.scheme eq "http")` |
| match path | `(http.request.uri.path matches "^/api/")` |

### target URL expressions

| goal | expression |
|------|------------|
| http→https | `concat("https://", http.host, http.request.uri.path)` |
| root→www | `concat("https://www.", http.host, http.request.uri.path)` |
| domain redirect | `concat("https://new.example.com", http.request.uri.path)` |

## anti-patterns [13][20][21]

### 1. redirect loops

> "Review your various redirect rules and Page Rules to make sure no rules are in conflict with each other" [20]

### 2. absent DNS records

> "You need a DNS record or the domain won't reach Cloudflare's servers so the redirect can be returned" [20]

### 3. hidden ruleset conflicts

> "Rulesets can create invisible conflicts preventing new rule creation via API/Terraform, though the dashboard works fine" [13]

**fix**: use REST API to identify and delete hidden rulesets

### 4. challenge loops

> "Cloudflare challenges along with Rules features may cause challenge loops... exclude URI paths at /cdn-cgi/challenge-platform/" [20]

## convergence signals

### sources [1][4][5][16] agree on:
- `http_request_dynamic_redirect` phase for zone-level redirects
- `action_parameters.from_value` structure with `target_url`, `status_code`, `preserve_query_string`
- `description` field for human-readable rule labels

### sources [8][14][15] agree on:
- PUT replaces entire ruleset (not incremental)
- must include all rules you want to keep
- rate limits prevent concurrent updates

---

## conflict detection

**sources [11] and [12] differ on scope**: [11] says "Ruleset permissions are at Account Level only" but [12] shows zone-specific "Dynamic URL Redirects" permission does extant. **decision**: use zone-level "Dynamic URL Redirects Write" permission.
